# Super Bunny: план переноса Unity → TypeScript

Дата: 1 ноября 2026. Документ предназначен для локальной модели, которая будет реализовывать перенос по небольшим проверяемым этапам.

Исходная игра: `/Users/trckwrk/Documents/vibe/Super Bunny`.
Новый проект: `/Users/trckwrk/Documents/vibe/Super Bunny JS`.

**Результат первой итерации:** самостоятельная браузерная игра на TypeScript с одним управляемым персонажем, физическим поведением текущей Unity-версии, сценой Physics Lab, подвесной грушей, захватами, прыжками, перекатами и текущей моделью P1. Игра собирается в обычные HTML/CSS/JS и запускается локально без Unity.

**Уточнение пользователя:** разворот персонажа по `S` исключён из этого плана. Не создавать для него систему, обработчик ввода, анимацию, параметры, заглушки или задачи. Направление профиля постоянно: `facing = +1`. Вращение тела в плоскости XY от `A/D`, кувырки и прыжки под наклоном сохраняются.

На момент составления документа выполнено чтение исходников, сцены, настроек и существующих тестов. Новая игра, экспорт GLB, установка пакетов и сравнительные запуски ещё не выполнены. Приведённые ниже критерии — требования к будущей реализации, а не отчёт о пройденных проверках.

- Существующие звуки прыжка, захвата, приземления и музыки; блокировка автозапуска звука браузером обрабатывается через действие пользователя.
- Отладочное изображение физических форм, контактных точек, суставов и центра масс.
- Запись входных действий по физическим тактам и воспроизводимое проигрывание без браузерного рендера.

В каждой сцене ровно один игрок. Полигон нужен для проверки механик, присутствующих в Unity, без переноса всех уровней и меню выбора карт.

Лиана и пружина входят в проверку одиночных взаимодействий. На основной сцене Physics Lab их не добавлять: её исходная компоновка должна сохраниться.

### За пределами первой итерации

Deathmatch, жизни, счёт, убийства ударом по голове, трупы, насаживание на шипы, победитель, таблица результатов, многопользовательское меню, все уровни, управление с геймпада и телефона, публикация на хостинге. В лаборатории падение на голову не убивает, как и сейчас в Unity. Полный перенос этих режимов возможен отдельной итерацией после проверки одиночной физики.

## 2. Выбранный стек

| Назначение | Выбор | Причина |
|---|---|---|
| Код игры | TypeScript, strict mode, ES modules | Явные типы тел, суставов, входа и снимков состояния; результат компилируется в JS |
| Физика | npm-пакет `planck` | JS/TS-реализация семейства Box2D; есть необходимые prismatic/revolute joints, моторы, лимиты, контакты и CCD |
| Рендеринг | `three`, `WebGLRenderer` | Сохраняет объёмную модель, скелетную деформацию, свет и перспективу при 2D-физике |
| Модели | GLB/glTF 2.0, `GLTFLoader` из Three.js | Подходит для переноса mesh, skin weights, skeleton и материалов |
| Сборка | `vite`, шаблон vanilla-ts или эквивалентная ручная настройка | Локальный dev server и статический production build |
| Проверки логики и физики | `vitest` в Node | Симуляция фиксированного числа тактов, проверки математики и сравнений траекторий |
| Проверки браузера | `@playwright/test` | Реальные клавиши, загрузка ресурсов, пауза, reset, отсутствие ошибок и визуальные снимки |
| Интерфейс | DOM + CSS | Для стартовой панели и нескольких кнопок UI-фреймворк не нужен |
| Звук | Web Audio API | Достаточно небольшого пула звуков; физика не зависит от аудио |
| Подготовка моделей | Установленный Blender, только offline export | Использует существующий `.blend`; не нужен для запуска готовой игры |

Planck выбран по структуре текущей игры: её `Rigidbody2D`, ползунковые ноги и шарнирные руки естественно переносятся на Box2D-подобный API. Это технический выбор для данного проекта, а не обещание побитового совпадения двух решателей. Официальное описание: [Planck.js](https://piqnt.com/planck.js/docs/index.html); правильное имя пакета — [planck](https://piqnt.com/planck.js/docs/install.html).

Three.js отвечает только за изображение. Его [WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html) требует WebGL 2; [GLTFLoader](https://threejs.org/docs/pages/GLTFLoader.html) загружает glTF/GLB. Выводить понятное сообщение, если WebGL 2 недоступен. В первой версии не подключать декодеры Draco/KTX2, чтобы не добавлять WASM-зависимости.

Не добавлять Unity WebGL, WASM-версию игрового движка, Phaser, React, ECS-фреймворк, сервер или сетевой протокол. Собственная физика с нуля также не нужна. Расчёт сил и правил написать на TS поверх Planck.

На первом этапе проверить совместимость выбранных стабильных версий Node, Vite и Vitest, зафиксировать точные версии зависимостей и `package-lock.json`. На дату проверки документация Vitest требует Node не ниже 22.12 и совместимый Vite; версии сверять при установке, не угадывать номера релизов. См. [Vite](https://vite.dev/guide/) и [Vitest](https://vitest.dev/guide/).

## 4. Что означает соответствие Unity

Сохранить геометрию, массы, распределение массы, направления осей, управление, время событий и реакции на контакты. Совпадение формы на скриншоте недостаточно: две модели с одинаковым силуэтом могут совершенно по-разному прыгать и висеть.

Сравнивать один и тот же вход, одинаковые начальные состояния, фиксированный шаг, одинаковые материалы и геометрию сцены. Проверять отдельно чистую физику и воспринимаемое движение со скином и камерой.

Различия версии Box2D, решения капсул, точности float/double и контактных допусков могут создавать расхождение. Цель — заданные ниже траектории и поведенческие ограничения, а не одинаковые двоичные состояния через много секунд хаотичных столкновений. Не маскировать ошибку адаптера произвольным изменением `jumpSpeed`, масс или сил.

### Сначала получить эталон

1. Создать отдельную временную копию Unity-проекта с текущим содержимым `Assets`, `Packages`, `ProjectSettings` и нужными инструментами. Не ограничиваться Git HEAD: иначе потеряются текущие изменения и Physics Lab.
2. Добавить измерительный код только в копию. Не пересобирать сцены и не вызывать сброс tuning: это может заменить сериализованные значения дефолтами.
3. Запустить одинаковые scripted input-сценарии без звука. Существующий runner поддерживает `test playmode <filter>` и использует `-mute`, но копию для измерителя подготовить явно: автоматический mirror runner создаёт лишь при занятом исходном проекте.
4. Экспортировать JSON с настройками мира, состоянием каждого тела после создания и после включения модели P1, а затем траектории по тактам.
5. Записать короткие видео/кадры с фиксированной камерой и отдельно с обычной игровой камерой. Зафиксировать viewport и масштаб.
6. Сохранить результат в новом JS-проекте под `reference/unity-runtime/`, вместе с идентификатором исходной базы, версией Unity, датой, сценой и сценарием.

Экспортировать `mass`, `centerOfMass`, `inertia`, transform origin, линейную/угловую скорость, gravityScale, damping, enabled/sensor-флаги коллайдеров, их контуры, локальные якоря, оси, reference angles, моторы и лимиты. Нужны также фактически действующие трение/упругость и глобальные ограничения решателя. Пол и груша не имеют явного PhysicsMaterial в исследованной сцене; их параметры нельзя автоматически приравнять к материалу тела персонажа.

В Unity действует версия редактора `6000.6.7f1`. Наличие локального редактора и Blender проверено при подготовке плана; возможность запуска и успешность экспорта ещё предстоит проверить. Если Unity недоступна, продолжать реализацию и перенос существующих тестов, но явно помечать сравнительную проверку `not run`, а не объявлять физическую идентичность.

## 6. Единицы, время и порядок выполнения

### Координаты и параметры мира

- Одна физическая единица = 1 метр; время в секундах, масса в килограммах.
- Физика в XY, `+Y` вверх, гравитация `(0, -7.8)`.
- `dt = 0.02`, то есть 50 физических тактов/секунду. Начальная настройка Planck: `world.step(0.02, 50, 3)`.
- `50` — число итераций velocity solver из `BunnyTuning.ApplyWorldSettings()`. Position iterations остаются `3` из `ProjectSettings/Physics2DSettings.asset`.
- Не брать `-9.81` и `8` velocity iterations из общих настроек проекта: при spawn код заменяет их tuning-параметрами.
- Итерации solver не являются подшагами. Не заменять шаг 20 мс на 60/120 Гц без отдельной калибровки и фиксации изменения.
- В C# углы тела/шарнира и угловая скорость представлены в градусах. В Planck — радианы. Переводить лимиты, скорости и показания в одном адаптере. Момент силы в Н·м не умножается на `DEG2RAD`.
- Ось Z нужна только рендерингу. Зафиксировать преобразование координат Unity ↔ Three. Удобная договорённость для мира: `(x,y,z)Unity → (x,y,-z)Three`; это отражение требует правильного преобразования ориентаций, а не только позиции камеры.

Способ задания шага и двух счётчиков solver описан в [Planck Simulation](https://piqnt.com/planck.js/docs/world/simulation.html). Использовать документацию установленной версии API, а не предполагать, что Unity-методы имеют то же имя.

### Главный цикл

1. Клавиатура обновляет held-состояния и запоминает переход `up → down`.
2. `requestAnimationFrame` добавляет прошедшее время в accumulator.
3. Пока accumulator ≥ 0.02, выполняется полный физический такт; одно нажатие потребляется только один раз.
4. После тактов рендер интерполирует предыдущую и текущую физическую позу с `alpha = accumulator / dt`.
5. В replay runner выполняется ровно заданное число тактов без `requestAnimationFrame`.

Для интерактивного режима ограничить разовый накопленный интервал и число догоняющих тактов, например 0.16 с / 8 тактов; считать и показывать отброшенное время в debug. Это явно выбранная защита браузерного цикла, не исходный Unity tuning. В обычной работе и при проверках 30/60/120/144 FPS лимит не должен срабатывать. Replay ничего не отбрасывает.

При `visibilitychange`/потере фокуса очищать зажатые клавиши и pending presses, замораживать симуляцию. При возврате сбрасывать wall-clock timestamp/accumulator, показывать паузу; не проигрывать накопившееся время. Эта адаптация предотвращает залипание ввода в браузере.

### Порядок одного такта

Unity не задаёт явный относительный порядок всех компонентов с обычным execution order. Поэтому зафиксировать порядок наблюдением в эталонном запуске и добавить его в metadata сценария. Важна следующая причинность:

1. Получить input и контакты завершённого предыдущего шага.
2. Обработать pause/reset вне заблокированного физического мира.
3. Применить события ввода, силы, изменение скоростей, параметры моторов, решение о захвате/отпускании; выполнить запланированные операции с суставами.
4. Выполнить `world.step`.
5. Собрать актуальные touching-контакты, обновить времена контактов и события удара; подготовить данные для следующего такта.
6. Обновить снимки и телеметрию; продвинуть визуальные пружины в той фазе, которая соответствует Unity baseline.

В исходнике `BunnyVisual.FixedUpdate` выполняется с order 100, до очередного Unity physics solve, и использует доступную на тот момент скорость. Прямой перенос обновления вторичной анимации после solve может сдвинуть её на один такт: либо сохранить фазу, либо явно отразить разницу в записи/сравнении. Для основной физики применять моторы до solver, а последствия новых контактов — после него.

Из contact callback нельзя создавать/удалять тела, fixture и joint во время `world.step`. Использовать очередь операций на безопасной границе такта. Проверить автоматическое очищение сил выбранной версией Planck: не переносить одну и ту же силу повторно по ошибке.

## 7. Физический персонаж: пять тел

| Тело | Количество | Масса каждого | Форма |
|---|---:|---:|---|
| Core | 1 | 6 кг | Вертикальная капсула торса + круг головы на том же теле |
| Leg | 2 | 1.2 кг | Горизонтальная капсула стопы |
| Arm | 2 | 0.4 кг | Круг кисти, смещённый относительно origin плеча |

Общая масса — 9.2 кг. Голова не отдельное rigid body. Видимые плечи, предплечья, бёдра и голени не добавляют новых физических тел. Живот также не отдельное тело.

### Геометрия и spawn

| Параметр | Значение в метрах |
|---|---|
| `coreCenter` | `(0, 0.53)` |
| `torsoSize` | `(0.36, 0.56)` |
| `headCenter`, `headRadius` | `(0.02, 0.87)`, `0.155` |
| `hip` | `(0.04, 0.36)` |
| `legSpread` | `0.09` |
| `footSize` | `(0.16, 0.11)` |
| `shoulder` | `(0.03, 0.77)` |
| `hand`, `handRadius` | `(0.39, 0.77)`, `0.06` |
| `linearDamping`, `angularDamping` | `0.05`, `0.05` |
| `bodyFriction`, `footFriction` | `0.4`, `0.9` |
| `bounciness` | `0` |

Точка spawn означает место подошв на земле. Формула исходника:

```text
base = spawnFeet + (0, footSize.y/2 + legRestLength - hip.y)
     = spawnFeet + (0, -0.085)
coreOrigin = base + coreCenter
hip[i] = hip + (i == 0 ? +legSpread : -legSpread, 0)
legOrigin[i] = base + hip[i] + (0, -legRestLength)
armOrigin[i] = base + shoulder
handLocal[i] = hand - shoulder = (0.36, 0)
headLocal = headCenter - coreCenter = (0.02, 0.34)
```

При `spawnFeet=(0,0)` origin Core находится на высоте `0.445`, центры стоп — на `0.055`, плечи — на `0.685`. Это начальная конструкция до settle, а не обещание точной высоты в покое. Индекс `0` — передняя физическая конечность, `1` — задняя.

Все части одного персонажа не сталкиваются друг с другом. Для Planck назначить отрицательный collision group только этому персонажу; маски должны пропускать Terrain и Props. Не отключать взаимодействие персонажа с предметами или столкновения несоседних звеньев цепи глобальной маской.

В текущей модели Sumo отсутствуют уши, и Unity отключает соответствующие невидимые сенсоры. Для V1 с Sumo такие сенсоры не создавать. Из-за этого массу/COM/inertia сравнивать с состоянием Unity после присоединения модели, а не только сразу после `BunnyRig.Build`.

### Капсулы, масса и инерция — первый технический риск

Planck не предоставляет Unity `CapsuleCollider2D` как готовый эквивалент. Начальный вариант адаптера — прямоугольник и два круга на одном теле, с общим `logicalColliderId`:

- Вертикальная капсула: `r = width/2`, центры кругов на `±(height/2-r)` по Y.
- Горизонтальная: `r = height/2`, центры на `±(width/2-r)` по X.
- При нулевой длине центрального сегмента использовать один круг.
- Параметры наружного контура не включают рендерный scale.

Перекрывающиеся fixture нельзя использовать для наивного суммирования площади и массы: так получится другая инерция. Явно привести `mass`, `localCenter` и `I` к измеренному Unity-значению через публичный mass-data API Planck. Проверить, относительно какой точки каждый API задаёт момент инерции, и при необходимости применить теорему параллельных осей. После изменения mass data проверить отсутствие случайного изменения скорости COM.

Дедупликация игровых событий не устраняет дополнительные контактные ограничения самого решателя. Если составная капсула меняет опору, качание или вызывает зацепы на стыках, это блокер этапа геометрии. Изучить разбиение округлого контура на неперекрывающиеся выпуклые полигоны с документированной погрешностью и лимитом вершин Planck; повторить контактные тесты. Нельзя компенсировать неверный контур скрытой балансирующей силой.

Отдельно проверить CCD для Core и стоп, поскольку в Unity у них Continuous. У рук в исходнике оно явно не включено. Для груши и всех её звеньев Continuous включено. Сверить поддерживаемые режимы Planck и поведение быстрых столкновений; не считать `bullet=true` доказательством полного соответствия.

### Ноги: prismatic joints

Для каждой ноги задать явно:

```text
bodyA = leg
bodyB = core
localAnchorA = (0,0)
localAnchorB = hip[i] - coreCenter
localAxisA = (0,1)
referenceAngle = 0
enableLimit = true
lowerTranslation = 0.14
upperTranslation = 0.32
enableMotor = true
```

При такой договорённости translation измеряется от стопы к бедру и в начальной позе равно `+0.22`. Не использовать convenience-конструктор с одним общим world anchor: он может дать нулевую translation и сломать смысл абсолютных длин. До подключения моторики сделать тест: начальная длина 0.22, положительная скорость мотора удлиняет ногу, вращение Core сохраняет направление оси в локальном пространстве.

Unity поле `JointMotor2D.maxMotorTorque` у SliderJoint фактически задаёт максимальную линейную силу. В Planck ему соответствует max motor **force**, а не torque. См. [Prismatic Joint](https://piqnt.com/planck.js/docs/joint/prismatic-joint.html).

### Руки: revolute joints

Договорённость, совпадающая со знаком Unity-показаний:

```text
bodyA = arm
bodyB = core
localAnchorA = (0,0)
localAnchorB = shoulder - coreCenter
referenceAngle = 0
jointAngle = coreAngle - armAngle
limits = [-75°, +75°], с переводом в радианы
```

При поднятии руки к голове справа показание шарнира отрицательное. Проверить это изолированным тестом до всей игры. Если выбран противоположный порядок тел, централизованно преобразовать знаки показаний и моторов; не расставлять случайные минусы в игровой логике. См. [Revolute Joint](https://piqnt.com/planck.js/docs/joint/revolute-joint.html).

## 8. Моторика: перенос алгоритмов

### Опора и контакты

`Grounded` означает: с момента последнего твёрдого контакта любой стопы прошло не более `0.1` с. В исходнике это не только контакт с полом и не только нормаль, направленная вверх. Касание стопой стены/предмета также обновляет время. Не добавлять фильтр `normal.y > threshold`: он изменит существующую механику.

`OnSurface` использует ту же задержку 0.1 с, но учитывает корпус, голову, стопы и свободные руки. Захваченная рукой поверхность не даёт ground torque через эту руку: персонаж продолжает висеть и раскачиваться с air torque.

Одного `begin-contact` недостаточно: Unity обновляет состояние и в `OnCollisionStay2D`. Каждый такт обработать все актуальные touching-контакты, включая покоящиеся тела. Сенсоры не считать опорой. Один контакт не должен дублироваться из-за нескольких fixture логической капсулы.

### Вращение

```text
roll = -1 при A; +1 при D; 0 при A+D или отсутствии клавиш
torque = -roll * (OnSurface ? 30 : 14) Н·м
```

Приложить момент только к Core. В Unity текущая угловая скорость Core ограничивается `±420°/с` перед очередным solve. Перенести фазу этого ограничения; не навешивать новый жёсткий clamp на все тела после каждого контакта. Глобальные ограничения самого решателя проверяются отдельно по runtime baseline.

Нет ускорения «ходьбы» по X, поддержания вертикальной позы, автоподъёма или кинематического перемещения. Короткое нажатие должно опрокинуть персонажа; удержание должно перекатывать его в обе стороны, включая ситуацию на лице и руках.

### Прыжок и толчок ногами

Один переход `W: up → down` потребляется один раз. Если в этот момент `Grounded=false`, событие теряется; отдельного jump buffer до приземления нет. Удержание W не создаёт повторные прыжки и не увеличивает высоту. Минимальный промежуток обычных прыжков — `0.15` с.

Прыжок направлен вдоль локальной оси вверх **физического** Core:

```text
up = (-sin(coreAngle), cos(coreAngle))
for each body of bunny:
  along = dot(body.velocity, up)
  if cancelDownwardVelocityOnJump && along < 0:
    velocity -= up * along
  velocity += up * 4.4
```

Это прибавка скорости всем пяти телам. Не применять один общий импульс только к Core, не умножать прибавку скорости на dt и не заменять её фиксированной мировой Y-компонентой. Поперечная составляющая сохраняется.

Перед прибавкой скорости персонажу проверить реальные контакты обеих стоп с чужими динамическими телами. Для каждого уникального предмета один раз:

```text
dir = -up
along = dot(other.velocity, dir)
if along < 0: other.velocity -= dir * along
other.velocity += dir * 7.1
```

Удар обрабатывается по контакту стопы, а не только по близости. Захват предмета сам по себе не считается таким контактом. Если обе стопы касаются одной груши, она не получает удвоенный толчок. Убийства и атаки по другому игроку в V1 отсутствуют.

После прыжка: `legsExtendUntil = now + 0.15`, `armsRelaxUntil = now + 0.22`, событие `Jumped`. Аналитическая оценка из `v=4.4`, `g=7.8` даёт подъём около 1.24 м и полёт около 1.13 с до исходной высоты, но итог зависит от ног и контактов: эталоном остаётся Unity-траектория.

### Моторы ног

| Состояние | Целевая длина | Ограничение скорости | Максимальная сила |
|---|---:|---:|---:|
| Первые 0.15 с после прыжка | 0.32 м | 6 м/с | 600 Н |
| Затем, если нет контакта стоп > 0.1 с | 0.16 м | 6 м/с | 220 Н |
| Остальные случаи, включая стойку | 0.22 м | 0.5 м/с | 220 Н |

На каждом такте для каждой ноги:

```text
motorSpeed = clamp(25 * (targetLength - jointTranslation), -speedLimit, +speedLimit)
```

Не заменять этот сервопривод физической SpringJoint с произвольной частотой: она может дать другую высоту и отскок. Ноги после приземления возвращаются медленно, чтобы не возникал бесконечный pogo-цикл.

### Моторы рук

- На новом твёрдом ударе со скоростью по нормали `>2 м/с` установить `armsRelaxUntil = now + 0.22`.
- `strengthTarget = Grounded && now >= armsRelaxUntil ? 1 : 0`.
- `strength = lerp(strength, strengthTarget, 1-exp(-14*dt))`.
- Свободная рука без захвата стремится к углу `0`; gain плавно меняется `1.2 → 4`, max torque `0.25 → 12 Н·м` по strength.
- Пока `Space` удерживается, свободная рука достигает рассчитанного угла цели с gain `12` и max torque `12 Н·м`, даже в воздухе.
- Уже удерживающая поверхность рука использует motor speed `0`, max torque `4 Н·м`; не фиксировать её жёстко в угле захвата.

Формула `motorSpeed = gain * (targetAngle-currentAngle)`. Если оба угла в радианах, результат в рад/с и gain численно тот же. Это важно для реального висения под руками: жёсткая фиксация плеча оставит тело горизонтально висеть в воздухе.

## 9. Захваты

Две руки работают независимо. У каждой может быть собственный шарнир к статической поверхности или динамическому телу. Вторая рука не дублирует физически первую, даже если их начальные координаты одинаковы.

### Выбор точки

1. Центр руки вычислить из physics transform Arm и `handLocal`, не из интерполированного mesh.
2. Найти подходящие collider в радиусе `handRadius + grabRadius = 0.15 м`.
3. Broadphase `queryAABB` — только поиск кандидатов. После него сделать точную проверку круг–форма и nearest point.
4. Исключить собственные части, зоны, UI-триггеры и объекты вне grabbable-категорий.
5. Выбрать наименьшее квадратное расстояние от руки до nearest point. При равенстве использовать стабильный ID, чтобы replay был воспроизводимым.
6. Compound-капсула считается одной логической формой: ближайшая точка определяется на наружном контуре, а не на внутреннем прямоугольнике внутри круга.

Для руки вне поверхности нормализовать `away = hand - surfacePoint`. Проверить точку `surfacePoint - away * (2.5 * handRadius)`:

- Если точка внутри логической формы, поверхность толстая: `grip = surfacePoint + away * handRadius`.
- Если снаружи, форма тонкая: `grip = surfacePoint - away * handRadius`.
- Если рука уже внутри и длина away почти нулевая, grip — текущий центр руки.

Это сохраняет исходное поведение: на широком полу кисть лежит поверх него, а тонкое звено проходит через зажатую кисть. Простое закрепление центра кисти на контуре утопит половину руки в земле.

### Шарнир захвата

Создать свободный revolute joint без собственного мотора и угловых лимитов. Якорь руки — `handLocal`; якорь цели — grip в локальном пространстве динамического тела или world point на статическом теле. `collideConnected=false`, как в Unity. Следить за тем, что подавление столкновений суставом может относиться к паре тел, а не одной fixture.

В tuning сила разрыва бесконечна. В JSON она сохранена строкой `"Infinity"`; в TypeScript преобразовать явно, а не получать `null` через `JSON.stringify(Infinity)`. В V1 не добавлять искусственное отрывание по расстоянию, силе или таймеру.

Отпускание `Space` удаляет оба удерживающих joint на безопасной границе шага и сохраняет текущие скорости. Reset освобождает все внешние связи до удаления игрока. Проверять уничтожение цели и отсутствие висячих ссылок.

### Дотягивание свободных рук

Поиск от origin плеча в радиусе `length(handLocal)+handRadius+grabRadius = 0.51 м`. Для каждого подходящего объекта найти ближайшую точку и вычислить:

```text
target = currentJointAngle - signedAngle(currentArmVector, directionToTarget)
```

Кандидата отвергнуть, если модуль target больше `armLimit + 15° = 90°`. Выбранную цель ограничить `[-75°,75°]`. Если подходящей поверхности нет, цель `-60°` при постоянном правом профиле. Поднятие рук, захват близкого низкого предмета и освобождение должны воспроизводить тесты Unity.

Не ограничивать поиск молча первыми несколькими broadphase-результатами. В Unity есть небольшие фиксированные буферы, но в JS лучше использовать переиспользуемый массив без случайной потери ближайшей поверхности. Такую разницу реализации записать в `DECISIONS.md`; в V1-сценариях она не должна менять выбор цели.

## 10. Лаборатория, предметы и восстановление

### Основная сцена

| Объект/параметр | Значение |
|---|---|
| Платформа | center `(0,-1.5)`, size `(16,3)`, верх на `y=0` |
| Spawn подошв P1 | `(-1.4,0)` |
| Верхнее крепление цепи | `(1.1,3.6)` |
| Число звеньев | 4 |
| Звено | вертикальная капсула `(0.08,0.4)`, масса 0.25 кг |
| Груша | вертикальная капсула `(0.7,1.35)`, масса 4 кг |
| Центр груши в покое | `(1.1,1.325)` |
| Damping всех звеньев и груши | linear 0.08, angular 0.15 |
| Recovery bounds | x от -12 до 12, y от -6 до 16 |
| Camera bounds | x от -14 до 14, y от -5 до 15 |

Центры звеньев при сборке: `(1.1,3.4)`, `(1.1,3.0)`, `(1.1,2.6)`, `(1.1,2.2)`. Первый joint соединяет верх первого звена со статическим world anchor; следующие — соседние звенья; последний — низ четвёртого звена и верх груши. Все шарниры свободные, `collideConnected=false`. Несоседние элементы по умолчанию могут взаимодействовать.

Цепь и груша действительно динамические. Не заменять их синусоидальной анимацией, одним pendulum-параметром или притягиванием к нарисованной верёвке. Кисть должна передавать нагрузку через настоящий joint.

Опора груши и верхняя балка в Unity созданы как декоративная 3D-геометрия. Не добавлять им новые 2D-препятствия. Для изображения перенести положения из `BuildLab`: стойка `(3.7,1.85,0.8)`, балка `(2.4,3.7,0.4)`, основание `(3.7,0.06,0.8)` в Unity-координатах.

### Reset и pause

`R` работает и из паузы, возвращая игру в рабочее состояние. Освободить захваты; удалить старого игрока; вернуть тела груши и цепи в начальные позиции и углы, обнулить скорости, разбудить их; создать одного нового игрока. Очистить input edges, времена контактов, arm strength, пружины, audio subscriptions и снимки интерполяции. Старый и новый игрок не должны одновременно участвовать в physics step.

После reset количество тел/joint/обработчиков должно вернуться к исходному. Служебное статическое тело учитывать отдельно: основная сцена содержит 10 динамических тел — 5 у игрока, 4 звена и грушу.

Пауза останавливает физическое время и вторичную анимацию, не только изображение. Нажатия прыжка в паузе не должны сработать после resume. Камера Unity использует unscaled delta time и может продолжать плавно приходить к framing; можно сохранить это поведение при замороженной позе.

Если Core вышел из recovery bounds или содержит NaN/Infinity, восстановить лабораторию. Нечисловое состояние дополнительно считать ошибкой в debug/report: auto-reset не должен скрывать нестабильность.

### Лиана на тестовой сцене

Источник — `ArenaBuilder.Vine` и `BunnyPhysicsTests.GrabHangsFromAVine`. Звенья: капсула `0.12 × 0.4`, масса `0.3 кг`, angular damping `0.5`, остальные параметры взять из фактических дефолтов Unity. Соседние звенья на свободных шарнирах; верх закреплён. Сценарий из теста использует 4 звена от `(0.4,3.2)` и игрока с подошвами `(0,1.6)` при удерживаемом захвате.

### Пружинная площадка на тестовой сцене

Перенести `SpringPad` как отдельный интерактивный объект:

- Площадка — kinematic body с box `0.8 × 0.14`; только контакты её верхней стороны запускают объект. Проверка исходника: `dot(contactPoint-padPosition, Up) >= thickness/4`.
- `launchSpeed=8 м/с`, `restLift=0.06`, `popLift=0.42`.
- Фазы: выдвижение `0.05 с`, удержание `0.5 с`, возврат `0.45 с`; повторное срабатывание после суммы этих фаз.
- Каждое тело персонажа получает `v += Up * max(0, 8-dot(v,Up))`. Уже большую скорость вдоль Up не снижать. Поперечную скорость сохранять.
- Дедупликация по игроку и динамическому предмету, а не по числу контактов.
- Перенести формулу `Lift(t)` из C#, включая затухающую вибрацию, в TS и двигать kinematic pad согласованно с физическим шагом. Не телепортировать площадку произвольно между кадрами.
- Проверить вертикальную площадку и наклон `30°`: вторая бросает игрока влево.

## 11. Модель, IK, мягкие движения и камера

### Экспорт модели

Для первой версии использовать Sumo из `ArtSource/sumo_rigged.blend`, поскольку именно он выбран текущим P1 и Physics Lab. Не перегенерировать персонажа по картинке. Экспортировать копию в `public/assets/models/sumo.glb`; исходный `.blend` и Unity FBX не перезаписывать.

Экспорт должен сохранить skin weights, иерархию, bind pose, материалы и кости `Root`, `Spine`, `Head`, `Belly`, `UpperArm.L/R`, `Forearm.L/R`, `Mitten.L/R`, `Thigh.L/R`, `Shin.L/R`, `Foot.L/R`. Если экспортёр меняет имена, сделать явную таблицу соответствий и проверку всех необходимых костей при загрузке. Отсутствующая кость — диагностическая ошибка, а не тихое отключение конечности.

До IK проверить единичный масштаб, положение ступней, высоту плеч и рук, направление лица, нормали и материалы. Подготовить фронтальный/боковой кадр bind pose рядом с Unity. Не исправлять неверный масштаб модели изменением физического мира.

GLB загружать локально, без CDN. Unity URP-материалы не переносить как исполняемые shaders: восстановить внешний вид стандартными материалами Three.js. Цвет кожи сохранить, одежда P1 красная; ориентир цвета игрока `(0.9,0.19,0.13)`.

### Привязка изображения к физике

- Корпус и голова следуют Core с исходным model offset `-coreCenter`.
- Постоянный профиль модели соответствует `ProfileYaw=65°` из Unity, с учётом преобразования координат.
- Таз получает дополнительный поворот в чистый профиль на 25°, позвоночник компенсирует его; перенести текущую постановку, чтобы дальняя нога не выглядывала неправильно.
- По две кости на руку и ногу решаются аналитическим IK из `BunnyVisual.TwoBone`.
- Длины костей брать из bind pose. Ограничивать reach диапазоном `|a-b|+0.001 .. a+b-0.001`, аргумент acos — `[-1,1]`.
- Локти сгибаются вниз, колени вперёд относительно профиля тела.
- Каждый расчёт начинается с bind rotation; не накапливать поворот прошлых кадров.
- Стопа сохраняет ориентацию физической подошвы, а не автоматически продолжает направление голени.

У свободных рук видимая кисть повторяет физический вектор руки от собственного видимого плеча, поэтому обе руки лежат рядом. При удержании или давлении на поверхность кисть подтягивается к действительному контакту. Для ног перенести `footGather`: в изображении обе ноги сходятся к общей опоре между физическими стопами либо к той стопе, которая сейчас касается поверхности. Саму физическую ширину опоры не менять.

Открытие кисти при дотягивании — до 25°, сжатие при захвате — до 50°, короткое визуальное сжатие/увеличение на 0.18 с с амплитудой 0.3. Перенести проверку поверхности возле кисти, чтобы варежка не проходила сквозь пол. Эти эффекты не создают дополнительных сил.

### Вторичная анимация

Перенести `InertialSpring2D` и расчёт живота/запястий из `BunnyVisual`:

| Параметр | Значение |
|---|---:|
| Belly frequency | 3 Гц |
| Belly damping ratio | 0.32 |
| Belly inertia | 0.4 |
| Belly travel | 0.055 м |
| Belly impact response | 0.12 |
| Wrist frequency | 3.8 Гц |
| Wrist travel | 16° |
| Wrist damping ratio | 0.45 |

Для Sumo коэффициент ткани `1`. У живота учитывается скорость точки привязки, включая вращение Core, а не только скорость origin. Импульс от самого сильного нового удара одного шага применяется один раз. Передача дельты скорости ограничивается так же, как в исходнике.

```text
omega = 2*pi*max(0.1, frequency)
steps = ceil(dt / (1/240))
h = dt/steps
for each internal step:
  velocity += (acceleration - omega²*offset - 2*damping*omega*velocity)*h
  offset += velocity*h
  if |offset| > limit:
    offset = normalize(offset)*limit
    удалить только наружную составляющую velocity
```

Это внутренние шаги визуальной пружины, не дополнительные шаги всего мира. При `dt=0` состояние сохраняется. Мягкое движение не должно менять gameplay collider, COM, положение головы или якоря захвата. У Sumo нет ушей/хвоста для отдельной анимации; не добавлять их ради старого Bunny-кода.

### Камера лаборатории

Перенести `SharedCamera.TryGetFocus` для Physics Lab: фокус включает игрока, AABB груши и верх цепи. Для игрока использовать границы `core.y-0.5` и `core.y+0.7`, как в исходнике.

- Perspective camera, FOV 30°, pitch 0°.
- Padding 0.65, minHeight 5.6, maxHeight 10, verticalBias -0.04.
- SmoothTime 0.35, ограничение camera bounds из сцены.
- Дистанция до XY-плоскости: `height / (2*tan(FOV/2))`.
- При изменении размеров окна менять aspect и вычислять framing заново; координаты физики не масштабировать.
- `SmoothDamp` переносить по поведению, а не заменять линейным lerp с произвольным коэффициентом на кадр.

Для замера физики предусмотрен фиксированный debug camera mode. Сравнение world-space траекторий не должно зависеть от плавающей камеры.

## 12. Браузер, UI и звук

Использовать `KeyboardEvent.code`: `KeyA`, `KeyD`, `KeyW`, `Space`, `KeyR`, `Escape`, `KeyQ`, чтобы игра работала при русской раскладке. `keydown.repeat` не создаёт новых jump edges. Одновременно A+D дают нулевой roll. Space и игровые клавиши не прокручивают страницу, когда активна игровая область; ввод в текстовых полях debug не перехватывать.

Минимальный UI: стартовая панель с кнопкой начала, нижняя строка управления, Reset, Pause/Resume, Mute. `Q` возвращает на стартовую панель и корректно освобождает мир/слушателей. Не воспроизводить многопользовательскую заставку с двумя физическими персонажами.

Скопировать существующие WAV в новый проект. Запуск AudioContext — после нажатия пользователя. Ограниченный пул голосов, отдельные уровни музыки/SFX. Для удара в Unity: minImpactSpeed `1.6 м/с`, общий интервал между land sounds `0.06 с`, громкость `clamp(speed/9,0,1)` с учётом общей громкости SFX. Начальные глобальные уровни сверить по `SfxLibrary.asset`.

Случайный выбор звука и pitch jitter не должны использовать RNG симуляции. Автоматические проверки запускать с выключенным звуком. Отсутствие аудиоустройства не останавливает игру.
